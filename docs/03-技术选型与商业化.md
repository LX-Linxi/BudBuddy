# 伴芽 BudBuddy — 技术选型与商业化方案 v0.1

> 本文对应互联网公司流程中的 **技术方案（TD）** 与 **商业模式设计**。
> TD 的作用是：把 PRD 的"做什么"翻译成"怎么做"，并**把技术风险提前暴露**。

# 第一部分：技术选型

## 一、选型决策：原生小程序 + 微信云开发

**结论先行：**

| 层 | 选择 |
|---|---|
| 前端 | 微信原生小程序（不用框架） |
| 后端 | 微信云开发（云函数 + 云数据库 + 云存储） |
| AI | 已备案的国产大模型 API（DeepSeek / 豆包 / 通义千问），在云函数内调用 |
| 知识库 | 云数据库存储 + 向量检索（初期可用关键词匹配代替） |
| 支付 | 微信支付（需企业/个体工商户主体） |

### 1.1 为什么不用 Taro / uni-app

你的情况是「有开发经验，但没做过小程序」。这个组合下，跨端框架是陷阱：

| 维度 | 原生 | Taro / uni-app |
|---|---|---|
| 学习成本 | 只学小程序一套心智模型 | 学框架 + 小程序两套，且要理解编译产物 |
| 调试链路 | 报错直指你的代码 | 报错可能在框架编译层，堆栈难读 |
| 文档与搜索 | 官方文档 + 海量社区答案 | 框架文档 + 版本碎片化，答案常过期 |
| 新 API 支持 | 第一时间可用 | 需等框架适配 |
| 迁移成本 | 后期若真要多端，改造量可控 | — |

**决策原则**：MVP 阶段，**你的时间是最稀缺资源**。跨端框架优化的是"未来可能的多端需求"，代价是"当下确定的调试痛苦"。用一个还没验证的假设去交换确定的成本，是典型的过度设计。

> 💡 **教学点：YAGNI（You Aren't Gonna Need It）**
> 不要为尚未发生的需求做架构。等真的需要 H5/App 时再迁 —— 那时你已经验证了产品，有资源做这件事；如果没验证成功，你还省下了这笔成本。

### 1.2 为什么用云开发而不是自建后端

自建后端（比如 Node + MySQL + 阿里云 ECS）你需要额外完成：

- 买服务器 + 域名 + **域名 ICP 备案**（约 5-20 工作日）
- 配 HTTPS 证书（小程序强制 HTTPS）
- 手写登录鉴权（code2session 换 openid、签发 token、刷新机制）
- 数据库部署、备份、连接池
- CI/CD、日志、监控

对独立开发者这是 **2-3 周的纯基础设施工作**，而且和产品价值零关系。

云开发把这些全包了：
- **免鉴权**：云函数里 `cloud.getWXContext().OPENID` 直接拿到用户身份，无法伪造
- **免运维**：无服务器、无备案（云开发调用不走 request 域名白名单）
- **免证书**：SDK 直连
- 有免费额度，MVP 阶段基本零成本

**风险与退路**：云开发绑定腾讯生态，量大后成本会高于自建。但云函数本质是 Node 函数，业务逻辑写得干净的话，后期迁移到自建服务只需替换数据库 SDK 和入口层。**做法：把业务逻辑写在纯函数里，云开发 API 只在最外层调用。**

```
云函数结构（可迁移写法）
├── index.js          ← 只做参数解析 + 调用 service（薄壳，迁移时重写这层）
├── service/
│   └── chat.js       ← 纯业务逻辑，不依赖 cloud SDK
└── dao/
    └── baby.js       ← 数据访问，集中封装 cloud.database()（迁移时只改这里）
```

### 1.3 大模型选型对比

| 模型 | 优势 | 注意 |
|---|---|---|
| **DeepSeek** | 中文强、价格极低、API 兼容 OpenAI 格式 | 需确认服务备案状态 |
| **豆包 Doubao**（火山引擎） | 腾讯/字节生态成熟、备案齐全、有 RAG 配套产品 | 价格中等 |
| **通义千问**（阿里云百炼） | 备案齐全、企业级 SLA、有现成向量检索 | 价格中等 |

**建议**：选型标准里，**"服务商已完成备案"权重高于"价格便宜 10%"**。上不了架，再便宜也没用。

实操：用同一组 20 个真实育儿问题跑三家，人工打分（专业性/安全性/口语化/长度），再看价格。这个过程叫 **模型评测集**，是 AI 产品的标准动作 —— 别凭感觉选。

### 1.4 关键技术点：为什么必须用 RAG 而不是纯生成

纯让大模型自由发挥育儿建议，会有三个致命问题：
1. **幻觉**：编造剂量、编造月龄标准
2. **不可控**：同一问题两次回答口径不一致，破坏"专业可信"定位
3. **无法举证**：出了问题你说不清依据来自哪

**RAG（检索增强生成）方案**：

```
用户提问
  → 向量化 / 关键词匹配
  → 从权威知识库检索 Top-3 片段（WHO 生长标准、膳食指南、免疫规划程序…）
  → 把片段作为「参考资料」塞进 Prompt
  → 模型基于资料作答，并附来源
```

**MVP 简化版**：初期不必上向量数据库。先把知识库按"月龄 × 主题"结构化存进云数据库，用规则匹配（月龄区间 + 关键词）召回，效果已经够用。等语料超过几百条再上向量检索。

> 💡 **教学点**：技术方案要分"MVP 版"和"演进版"。先用最笨但能跑的方案上线拿数据，再优化。过早上向量库是另一种过度设计。

## 二、数据库设计（云数据库集合）

```javascript
// users —— 用户
{
  _id, _openid,              // _openid 由云开发自动写入，是天然的用户主键
  nickname, avatarUrl,
  vipUntil: Date,            // 会员到期时间，null 表示非会员
  createdAt, lastActiveAt
}

// babies —— 宝宝档案
{
  _id, _openid,              // 创建者
  nickname,
  birthday: Date,
  gender: 'male' | 'female',
  avatarUrl,
  allergies: [String],       // 过敏史，渐进式收集
  birthWeight, birthHeight,
  memberOpenids: [String],   // 家庭共享成员（v1.1）
  createdAt
}

// records —— 记录（高频写入，注意索引）
{
  _id, _openid, babyId,
  type: 'feed' | 'sleep' | 'diaper' | 'growth',
  // feed:   { amount: 120, unit: 'ml', method: 'bottle'|'breast' }
  // sleep:  { startAt, endAt, duration }
  // diaper: { texture, color }
  // growth: { weight: 8.2, height: 70, head: 44 }
  payload: Object,
  occurredAt: Date,          // 实际发生时间（≠ 创建时间，用户可补录）
  createdAt: Date
}
// 索引：{ babyId: 1, occurredAt: -1 }  ← 必建，否则列表查询会全表扫描

// conversations —— AI 对话
{
  _id, _openid, babyId,
  messages: [{ role: 'user'|'assistant', content, at, feedback }],
  contextSnapshot: Object,   // 提问时的宝宝月龄等，便于回溯分析
  createdAt, updatedAt
}

// quotas —— 用量配额（防刷 + 成本控制）
{
  _id, _openid,
  date: '2026-08-11',
  askCount: 3
}
// 索引：{ _openid: 1, date: 1 } 唯一

// knowledge —— 知识库
{
  _id,
  topic: 'feeding' | 'sleep' | 'development' | 'health' | 'safety',
  ageMinDays, ageMaxDays,    // 适用日龄区间
  title, content,
  source: 'WHO 儿童生长标准',
  keywords: [String]
}

// daily_cards —— 每日卡片（可缓存，避免重复生成）
{ _id, babyId, date, cards: [{ type, icon, title, content }] }

// orders —— 订单
{ _id, _openid, sku, amount, status, wxTransactionId, createdAt, paidAt }
```

> 💡 **教学点：为什么 `occurredAt` 和 `createdAt` 要分开？**
> 用户可能晚上补录白天的喂奶。业务时间和系统时间必须分离 —— 这是所有记录类产品的通用设计，很多新手会踩这个坑，导致数据分析时全错。

## 四、开发规范（提升工程素养的部分）

### 4.1 Git 分支模型（简化版 Git Flow）

```
main        ← 生产，只接受 release 合入，每次合入打 tag
  ↑
develop     ← 集成分支，日常开发合入这里
  ↑
feature/*   ← 功能分支，如 feature/ai-chat
hotfix/*    ← 线上紧急修复，从 main 拉，修完合回 main + develop
```

个人项目也要这么做，理由：培养肌肉记忆，且能保证 `main` 永远是可发布状态。

### 4.2 Commit 规范（Conventional Commits）

```
<type>(<scope>): <subject>

feat(chat): 支持 AI 流式输出
fix(record): 修复补录时间早于生日时崩溃
refactor(cloud): 抽离 dao 层以便后期迁移
docs(prd): 补充埋点清单
chore(deps): 升级基础库版本
```

好处：`git log --oneline` 就是一份自动生成的 changelog，且能自动化生成版本说明。

### 4.3 Code Review 自查清单

个人项目没有 reviewer，就自己做 **PR 自查**（把 diff 完整读一遍再合）：

- [ ] 有没有硬编码（尤其 API Key、魔法数字）
- [ ] 有没有未处理的异常分支（网络失败、空数据、超时）
- [ ] 有没有 N+1 查询 / 缺索引的查询
- [ ] 有没有把用户输入直接拼进 Prompt（Prompt 注入风险）
- [ ] 埋点是否跟着功能一起加了
- [ ] 有没有加载态和空态（新手最常忘的两个态）

> 💡 **教学点：页面必须有四态**
> 加载中 / 有数据 / 空数据 / 出错。绝大多数业余项目只写了"有数据"这一态，一到真实网络环境就白屏。这是区分业余和专业最直观的一条。

# 第二部分：商业化方案

## 五、收费模式设计

### 5.1 模式选择：Freemium 订阅制

为什么不是其他模式：

| 模式 | 判断 |
|---|---|
| 广告 | ❌ 需要巨大流量才有收入，且伤害"专业中立"定位 |
| 电商 | ❌ 需供应链与资质，非能力圈 |
| 内容付费（单篇买断） | ⚠️ 可作补充，但复购弱、LTV 低 |
| **Freemium 订阅** | ✅ 与"持续陪伴"的产品形态天然契合，现金流可预测，且已被 Huckleberry（年费约 $59）等验证 |

### 5.2 定价方案

| 档位 | 价格 | 权益 |
|---|---|---|
| **免费** | ¥0 | 每日 3 次 AI 提问 · 无限记录 · 每日成长卡片 · 生长曲线 |
| **月度会员** | ¥28/月 | 无限提问 · 周报月报 · 深度趋势分析 · 多宝宝 · 家庭共享 · 无广告 |
| **年度会员** | **¥168/年**（合 ¥14/月） | 同上 + 年度成长纪念册 |
| **单次深度报告** | ¥9.9-19.9 | 睡眠改善方案 / 辅食计划 / 入园准备清单（非会员可单买） |

**定价逻辑**：
- 锚点参考：孩子王付费会员 99 元/年（轻享）、199 元/年（畅享）；¥168 落在这个被市场教育过的区间内
- 月卡定 ¥28 而非 ¥19，是为了**让年卡显得划算**（¥168 vs ¥336，5 折）—— 这是标准的价格锚定，目的是把用户推向年卡以提升现金流与留存
- 免费额度 3 次/日：够解决日常疑问（形成习惯），不够应对高频焦虑期（形成付费动机）

### 5.3 付费转化触点设计

付费墙不能只放在"我的"页面里等用户自己发现。三个高意愿时刻：

| 触点 | 时机 | 文案方向 |
|---|---|---|
| **配额耗尽** | 第 4 次提问时 | "今天的免费提问用完了 · 开通会员随时问" |
| **周报预览** | 周日推送周报，只展示前 1/3 | "小芽本周的睡眠有个变化…… 解锁完整报告" |
| **趋势异常** | 检测到生长曲线百分位下滑 | "小芽的体重曲线有变化，查看详细分析" |

第 2 和第 3 个触点转化率通常远高于第 1 个 —— 因为它们提供的是**用户不知道自己需要的信息**，而第 1 个只是解除限制。

## 六、单位经济模型（Unit Economics）

> 💡 **教学点**：任何商业模式，在写第一行代码前就该算这笔账。算不通就别做。

### 6.1 成本测算（每用户每月）

**AI 成本**
- 单次问答约：输入 2,000 token（含档案+知识库片段）+ 输出 800 token
- 国产模型价格量级：约 ¥0.001-0.005 / 千 token
- 单次成本 ≈ **¥0.01**（取中位）

| 用户类型 | 用量 | 月 AI 成本 |
|---|---|---|
| 免费用户 | 3 次/日 × 30（上限） | ≤ ¥0.9（实际活跃度低，均值约 ¥0.2） |
| 会员用户 | 实测约 8 次/日 | ≈ ¥2.4 |

**其他成本**（云开发按量计费，1 万用户量级）
- 数据库读写 + 存储 + 云函数：约 ¥100-300/月
- 摊到人头：< ¥0.03/人/月

### 6.2 毛利测算

```
年卡用户：
  收入  ¥168/年 = ¥14.0/月
  微信支付手续费 0.6%      -¥0.08
  AI 成本                  -¥2.40
  基础设施                 -¥0.03
  ──────────────────────────────
  毛利  ≈ ¥11.5/月  →  毛利率 82%   ✅ 健康

免费用户（成本中心）：
  月均成本 ≈ ¥0.23
  按 3% 付费转化算，每个付费用户需承担 32 个免费用户的成本
  = ¥0.23 × 32 ≈ ¥7.4/月
  ──────────────────────────────
  综合毛利 ≈ ¥14.0 - ¥7.4 - ¥2.5 = ¥4.1/月  →  仍为正 ✅
```

**结论：模型跑得通，但免费额度是成本杠杆。** 如果转化率跌到 1%，每个付费用户要养 99 个免费用户（¥22.8/月），**模型立刻转负**。

**因此三条铁律：**
1. 免费额度必须有硬上限（3 次/日，且必须在服务端校验，不能只在前端拦）
2. 必须监控"免费用户 AI 成本 / 付费收入"这个比值
3. 转化率跌破 2% 要立刻收紧免费额度

### 6.3 盈亏平衡点

假设年运营成本（主体年费、模型最低消费、域名等）约 ¥5,000：

```
盈亏平衡付费用户数 = 5000 / (¥4.1 × 12) ≈ 100 个付费用户
按 3% 转化率 → 约 3,400 注册用户即可打平
```

这个数字对独立开发者是**可达的**。这也是为什么 PRD 的 KR1 定在 3,000 注册。

## 七、必须现在就启动的合规事项

| 事项 | 周期 | 备注 |
|---|---|---|
| **注册个体工商户 / 公司** | 1-2 周 | 微信支付硬前置。个体工商户成本最低 |
| **小程序 ICP 备案** | 5-20 工作日 | 2023 年起小程序强制备案 |
| **选择已备案的大模型服务** | — | 用服务商的备案，避免自己去做算法备案 |
| **AI 生成内容标识** | 开发时实现 | 2025 年 9 月起强制，所有 AI 输出需显式标注 |
| **隐私政策 + 用户协议** | 1 天 | 涉及儿童信息，需明示收集范围与用途 |
| **服务类目选择** | 提审时 | **避开医疗类目**，按工具/教育申报，产品内严禁诊疗表述 |

> ⚠️ **最大的项目风险不是技术，是合规。** 很多个人开发者做完发现上不了架。这份清单请在写代码之前就动起来 —— 备案是等待时间，可以和开发并行。
