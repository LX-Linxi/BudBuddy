## 📖 先读这段：PRD 到底是什么

在互联网公司里，PRD 是**产品和研发之间的契约**。它的读者是研发、测试、设计、运营，不是老板。

一份合格 PRD 的判据只有一条：**研发看完能开始写代码，测试看完能开始写用例，中间不需要再来问你。**

因此 PRD 必须包含（也只需要包含）：

1. 背景与目标 —— 为什么做（防止研发做出正确但没用的东西）
2. 用户与场景 —— 给谁用、在什么情况下用
3. 功能需求 —— 做什么，**带优先级**
4. 交互与流程 —— 怎么走
5. 非功能需求 —— 性能、安全、合规
6. 数据指标 —— 怎么判断做成了
7. 不做什么 —— **和"做什么"同等重要**

新人 PRD 最常见的三个病：① 只有功能列表没有优先级；② 没有"不做什么"；③ 没有验收标准。下面每一节都会刻意示范怎么避开。

## 一、背景与目标

### 1.1 背景

见 `01-市场与竞品分析.md`。一句话概括：母婴赛道存在"专业性 × 个性化 × 实时性"的结构性空白，现有产品各占其一，无人占全。

### 1.2 产品定位

> 伴芽是一个"记得你家娃"的科学育儿顾问。

### 1.3 目标（OKR 式）

**O：验证"带记忆的 AI 育儿顾问"是真需求**

| KR | 目标值 | 说明 |
|---|---|---|
| KR1 | 上线 3 个月内注册用户 ≥ 3,000 | 冷启动验证 |
| KR2 | 次日留存 ≥ 35%，7 日留存 ≥ 20% | 低于此说明价值不成立，需回炉 |
| KR3 | 建档用户中，周均 AI 提问 ≥ 3 次 | 验证 AI 是真钩子 |
| KR4 | 付费转化率 ≥ 3% | 验证商业模式 |

> 💡 **教学点**：目标必须可证伪。"提升用户体验"不是目标，"次日留存 ≥ 35%"才是。写不出数字，通常说明你还没想清楚要做什么。

## 二、用户画像与场景

### 2.1 目标用户

**核心用户（P0）— 新手妈妈「小林」**

- 30 岁，新一线城市，本科以上，产假中或刚返岗
- 娃 6 个月，首胎，无育儿经验
- 焦虑源：喂养量对不对、睡眠不好是不是缺钙、发育有没有落后
- 行为：每天在小红书搜 5-10 个育儿问题，收藏一堆但记不住；手机里装过 3 个记录 App，全都用了两周就放弃
- 付费意愿：**高**。为孩子花钱决策阈值远低于为自己花钱

**次要用户（P1）— 参与型爸爸**
想帮忙但不知道做什么，需要"今天该干嘛"的明确指令。是家庭共享功能的使用者。

**边缘用户（P2）— 祖辈照护者**
不主动使用，但是"育儿分歧"场景的另一方。**不为其做适配**，只把内容做成可转发形态。

### 2.2 核心场景（用户故事）

| ID | 场景 | 用户故事 |
|---|---|---|
| S1 | **深夜急问** | 作为新手妈妈，当娃凌晨发烧时，我想立刻得到可靠的处理建议，以便判断是观察还是去医院 |
| S2 | **日常疑问** | 作为新手妈妈，当我不确定娃能不能吃某样东西时，我想快速得到基于我娃月龄和过敏史的答案 |
| S3 | **发育对照** | 作为新手妈妈，我想知道我娃的身高体重和发育情况在同龄中处于什么位置，以便安心或及时干预 |
| S4 | **顺手记录** | 作为新手妈妈，我想用最少的操作记下喂奶/睡眠，以便回头看规律，而不是变成负担 |
| S5 | **预期管理** | 作为新手妈妈，我想提前知道下个阶段会发生什么，以便做好准备而不是临时慌乱 |
| S6 | **说服家人** | 作为新手妈妈，当和长辈育儿观念冲突时，我想有一份权威说法可以转发过去 |

## 三、功能需求

### 3.1 功能全景

```
伴芽 BudBuddy
├── 🏠 首页          今日卡片 / 快捷记录入口 / AI 入口
├── 🌱 成长          发育里程碑 / 生长曲线 / 阶段指南
├── 📝 记录          喂养 / 睡眠 / 尿布 / 身高体重
├── 🤖 AI 助手       带档案上下文的多轮对话
└── 👤 我的          宝宝档案 / 会员 / 家庭共享 / 设置
```

### 3.2 需求池与优先级（MoSCoW）

> 💡 **教学点：MoSCoW 法**
> - **Must have** — 没有它产品不成立，砍了就别上线
> - **Should have** — 重要但可延后一个版本
> - **Could have** — 锦上添花，有时间才做
> - **Won't have (this time)** — **明确写下来不做**，这一列是防止需求蔓延的护栏
>
> 判断标准：如果这个功能砍掉，用户还会用吗？会 → 不是 Must。

#### ✅ Must have（MVP / v1.0）

| ID | 功能 | 说明 | 验收标准 |
|---|---|---|---|
| M1 | **宝宝档案** | 昵称、生日、性别、头像、过敏史、出生体重身高。支持多宝宝（上限 2） | 新用户首次打开引导建档，30 秒内可完成；档案数据被 AI 与卡片正确引用 |
| M2 | **AI 育儿问答** | 多轮对话，自动注入宝宝档案 + 最近 7 天记录摘要作为上下文 | 首字响应 ≤ 2s；回答显式标注「AI 生成」；涉及症状时输出就医提示 |
| M3 | **今日成长卡片** | 每天按精确日龄生成 3 张卡片：喂养建议 / 睡眠建议 / 发育重点 | 打开首页即见；内容随日龄变化；可长按分享为图片 |
| M4 | **快捷记录** | 喂奶、睡眠、尿布、身高体重。**核心要求：主流程 ≤ 2 次点击** | 从首页到完成一条喂奶记录 ≤ 2 次点击；睡眠支持开始/结束打点 |
| M5 | **生长曲线** | 身高/体重/头围对照 WHO 标准曲线，显示百分位 | 至少 2 个数据点即出图；百分位计算误差 < 1% |
| M6 | **登录与账号** | 微信静默登录（openid），无需手机号 | 首次打开无需任何输入即可浏览；建档时才落库 |

#### 🔶 Should have（v1.1）

| ID | 功能 | 说明 |
|---|---|---|
| S1 | **发育里程碑自查** | 按月龄给出里程碑清单（参考 WHO/丹佛量表简化版），勾选式自查，落后项给出提示与建议 |
| S2 | **记录趋势分析** | 喂养/睡眠的周视图、规律识别（如"最近入睡时间推迟了 40 分钟"） |
| S3 | **周报 / 月报** | AI 汇总本周记录 + 发育情况，生成可分享的图文报告 —— **这是主要付费点** |
| S4 | **家庭共享** | 邀请码加入同一宝宝档案，多人共同记录与查看 |

#### 🔷 Could have（v1.2+）

| ID | 功能 | 说明 |
|---|---|---|
| C1 | 成长相册 | 按时间线的照片记录 |
| C2 | 疫苗接种提醒 | 按国家免疫规划程序推送 |
| C3 | 辅食库 | 按月龄的食材可食性查询 + 食谱 |
| C4 | 深度报告（单次付费） | 睡眠改善方案、辅食计划、入园准备清单 |

#### ❌ Won't have（v1 明确不做，附理由）

| 功能 | 不做的理由 |
|---|---|
| **社区 / UGC** | 冷启动极难（没人发帖就没人来），内容审核合规成本高，且与"专业可信"定位冲突。这是最容易吸引人做、也最容易拖死项目的功能 |
| **电商 / 好物推荐** | 需要供应链和资质，且会稀释专业中立性，重蹈宝宝树的路 |
| **视频课程** | 内容生产成本高，非独立开发者能力圈 |
| **医生在线问诊** | 需要《医疗机构执业许可证》，合规门槛不可逾越 |
| **手机号注册 / 复杂登录** | 增加流失，微信 openid 已足够 |
| **多端（H5 / App）** | MVP 阶段验证优先，不为多端做技术妥协 |

> 💡 **教学点**：Won't have 这一列的价值 > Must have。绝大多数个人项目死于"顺便再加个功能"。把不做的事写下来并签字，是对未来的自己最有用的约束。

## 四、核心流程设计

### 4.1 新用户首次进入（激活流程）

```
打开小程序
   ↓
静默登录（无感，获取 openid）
   ↓
是否已有宝宝档案？
   ├─ 否 → 引导页：「宝宝的小名是？」→「生日是？」→「性别？」
   │        （3 步，每步一个问题，可跳过过敏史）
   │        ↓
   │      生成首张今日卡片 → 首页
   └─ 是 → 首页
```

**设计原则**：
- 建档必须在 30 秒内完成，只问最少必要信息（昵称/生日/性别）
- **不要在这里问过敏史、出生体重** —— 放到第一次用到时再问（渐进式收集）
- 完成建档立即给正反馈：显示"小芽已经 259 天啦"+ 首张卡片

> 💡 **教学点**：激活流程是留存的第一道闸。每多一个必填项，流失约 10-20%。永远问最少的问题。

### 4.2 AI 问答流程

```
用户提问
   ↓
前端组装：{ 问题, babyId }
   ↓
云函数：
   1. 校验用量配额（免费用户 3 次/日）
   2. 拉取宝宝档案 + 近 7 天记录摘要
   3. 检索知识库（RAG）→ 取 Top-K 权威片段
   4. 拼装 System Prompt（含安全约束）→ 调用大模型（流式）
   5. 落库对话记录 + 扣减配额
   ↓
前端流式渲染 + 底部固定标注「内容由 AI 生成，不能替代医生诊断」
```

**System Prompt 安全约束（必须硬编码）**：
- 不给出药物名称与剂量
- 不做疾病诊断
- 出现发热 >3 天、抽搐、呼吸困难、拒食、精神萎靡等红旗症状 → 强制输出"立即就医"
- 回答须基于检索到的知识库内容，无依据时明确说"这个问题建议咨询儿科医生"

### 4.3 快捷记录流程（留存关键）

```
首页 → 记录条（常驻，无需进二级页）
   ├─ [🍼 喂奶]  单击 → 弹出数量选择器 → 确认   (2 击)
   ├─ [😴 睡眠]  单击 → 立即开始计时；再击结束    (1 击)
   ├─ [💩 尿布]  单击 → 选择类型 → 确认          (2 击)
   └─ [📏 体重]  单击 → 输入 → 确认              (低频，可 3 击)
```

**设计原则**：默认值优先。喂奶量默认上次的值，时间默认当前时间。让用户"确认"而不是"填写"。

## 五、非功能需求

| 类别 | 要求 |
|---|---|
| **性能** | 首页首屏 ≤ 1.5s；AI 首字响应 ≤ 2s（必须流式，不能转圈等全文） |
| **兼容** | 微信基础库 ≥ 2.30.0；iOS 14+ / Android 8+ |
| **安全** | 大模型 API Key **仅存于云函数环境变量**，绝不出现在前端代码或代码仓库；数据库按 openid 做行级权限 |
| **隐私** | 首次建档前展示《隐私政策》并获取授权；宝宝照片/生日属敏感信息，需明示用途；提供账号与数据删除入口 |
| **合规** | ① AI 生成内容全局标注 ② 使用已完成备案的模型服务 ③ 不涉及诊疗，类目按"教育-在线教育"或"工具"申报，避开医疗类目 |
| **可用性** | AI 服务不可用时降级为"知识库检索结果"而非报错白屏 |
| **成本** | 单免费用户月均 AI 成本控制在 ¥0.5 以内（靠配额限制） |

## 六、数据指标体系

> 💡 **教学点：北极星指标（North Star Metric）**
> 一个产品只能有一个北极星指标。它必须同时满足：① 反映用户获得的价值 ② 与营收正相关 ③ 团队能通过行动影响它。
> DAU 通常不是好的北极星 —— 它可以靠 push 骚扰刷高，但不代表用户获得了价值。

**北极星指标：周活跃有效用户数（WAU-Active）**
定义：一周内 **提问 ≥ 1 次 或 记录 ≥ 3 条** 的用户数。

### 指标拆解（AARRR 模型）

| 阶段 | 指标 | 目标 |
|---|---|---|
| **Acquisition 获客** | 新增用户数、来源渠道分布 | — |
| **Activation 激活** | 建档完成率 | ≥ 70% |
| | 首日发生 ≥1 次提问或记录的比例 | ≥ 50% |
| **Retention 留存** | 次日 / 7日 / 30日留存 | 35% / 20% / 12% |
| | 周记录天数分布 | 中位数 ≥ 3 天 |
| **Revenue 收入** | 付费转化率、ARPPU、续费率 | 3% / ¥150 / 40% |
| **Referral 传播** | 卡片分享次数、分享带来的新增占比 | 分享率 ≥ 8% |

### AI 质量专项指标

- 单会话平均轮次（追问说明有价值，目标 ≥ 2.5）
- 回答点赞率 / 点踩率
- 触发"建议就医"的比例（过高说明 prompt 过度保守，过低说明有安全风险）

### 埋点清单（开发时同步实现）

| 事件名 | 触发时机 | 参数 |
|---|---|---|
| `app_launch` | 小程序启动 | scene, from |
| `baby_profile_complete` | 完成建档 | step_count, duration |
| `record_create` | 创建记录 | type, entry(首页/记录页) |
| `ai_ask` | 发起提问 | baby_age_days, question_len, is_vip |
| `ai_answer_feedback` | 点赞/点踩 | message_id, value |
| `card_share` | 分享卡片 | card_type |
| `paywall_view` | 看到付费墙 | trigger(配额耗尽/周报/主动) |
| `purchase_success` | 支付成功 | sku, amount |

> 💡 **教学点**：埋点必须在 PRD 阶段就定义好，跟着功能一起上线。事后补埋点意味着丢掉一整个版本周期的数据。

## 附录：本次代码现状评估

对已有代码的检查结论（`miniprogram/`）：

**现状**：微信官方模板脚手架 + 4 个页面骨架，`home.js` 内有硬编码的假数据，无后端、无逻辑。约等于起步阶段。

**发现的问题**（在 M1 开始前需清理）：

| # | 问题 | 影响 |
|---|---|---|
| 1 | `home.json` 声明使用组件 `/components/baby-card/baby-card`，但 **`components/` 下只有 `navigation-bar`，`baby-card` 不存在** | 编译报错 / 首页组件区块渲染失败 |
| 2 | `pages/index/` 存在但未在 `app.json` 注册 | 官方模板残留，应删除 |
| 3 | `pages/profile/` 下同时有 `index.wxml` 和 `profile.wxml` | 重复文件，`index.wxml` 应删 |
| 4 | `pages/guide/` 下同时有 `index.wxss` 和 `guide.wxss` | 同上 |
| 5 | `tabBar` 未配置 `iconPath` / `selectedIconPath` | 纯文字 tabBar，观感差 |
| 6 | `home.js` 中 `age`（"8个月16天"）、`growthDays`（259）为写死字符串 | 应由生日实时计算，这是我们要写的第一个工具函数 `utils/date.js` |
| 7 | `home.wxml` 的 `suggestions` / `quickEntries` 全为静态假数据，快捷入口无 `bindtap` | 无任何交互，需接入真实数据与路由 |
| 8 | 页面无加载态 / 空态 / 错误态 | 真实网络环境下会白屏，见「页面四态」 |
| 9 | `"renderer": "webview"` 前有多余空格 | 无害但不规范 |

这些会在下一步「技术方案 + 环境清理」中逐条处理。
